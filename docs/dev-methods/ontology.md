# オントロジー — AI エージェントに業務知識を渡す

> **対象ツール**: ツール横断 ｜ **実行環境**: CLI / Cloud ｜ **対象読者**: エンジニア・データ担当 ｜ **最終更新**: 2026-08-29

> エージェントが業務で外す原因は、モデルの賢さより「渡している情報に業務上の意味がない」ことにあります。**オントロジー**は、その意味 — 語彙・関係・規則 — を機械が読める形で定義する枠組みです。このページは、オントロジーとナレッジグラフ・RAG の違い、いつ必要でいつ不要か、そして AI エージェントでの具体的な使いかたを整理します。哲学や情報科学一般としてのオントロジー論は扱いません。最近の動きだけを追いたい場合は [Skills 最新動向 11 節](../trends.md#11-エージェントに渡す知識オントロジー) を参照してください。

---

## いつ必要で、いつ不要か

オントロジーの構築は安い作業ではありません。先に、それが要る状況かを判断してください。

| 状況 | 判断 |
|------|------|
| 同じ言葉が部署ごとに違う意味を持つ（「契約」「顧客」「稼働中」） | **要る**。定義を 1 か所に固定しないと、エージェントの出力が部署ごとに食い違う |
| 「A と B を共通の属性でつなぐ」問いに答えさせたい | **要る**。ベクトル検索は近い文書を引くだけで、関係をたどれない |
| 出力の根拠を説明・監査する必要がある（金融・医療・公共） | **要る**。どの定義と規則に基づく答えかを示せる |
| 規則違反の検出をさせたい（この状態遷移は許されるか） | **要る**。論理的な制約として書ける |
| 文書を検索して要約させたい | 不要。素直に RAG で足りる |
| 対象が 1 チームの狭い範囲で、用語のゆれがない | 不要。`SKILL.md` やプロジェクト文書で足りる（[Claude Code のカスタマイズ機能](../claude-code/basics.md)） |
| `SKILL.md` では足りないが、形式的な定義を組むほどでもない | 中間がある。Markdown をそのまま知識の源にする[記憶層](#形式的な定義を作らない選択肢--gbrain)で始める |
| 定義を継続的に維持する担当を置けない | **やめる**。放置されたオントロジーは、古い定義で誤りを量産する |

## 用語の切り分け

この 4 つは混同されがちですが、指しているものが違います。

| 用語 | 指すもの | 一言でいうと |
|------|---------|-------------|
| **オントロジー** | クラス・プロパティ・階層・論理公理の**定義** | 語彙と規則 |
| **ナレッジグラフ** | 実体と関係の**データ**（ノードとエッジ） | 中身 |
| **RAG** | 質問に近い文書片をベクトル検索でプロンプトへ足す**手法** | 引いて渡す |
| **GraphRAG** | 検索対象をグラフとその要約にする**手法** | たどって渡す |

要点は、**オントロジーが定義、ナレッジグラフがデータ**という関係です。オントロジーは「注文は顧客に属し、状態は 未処理 / 出荷済 / 取消 のいずれかを取る」と決め、ナレッジグラフは「注文 #123 は顧客 A に属し、状態は 出荷済」というデータを持ちます。

標準は W3C の [RDF](https://www.w3.org/TR/rdf11-concepts/)（データモデル。主語・述語・目的語のトリプル）と [OWL 2](https://www.w3.org/TR/owl2-overview/)（その上の記述論理。クラス・制約・推論）です。まずこの 2 つの名前だけ知っていれば、製品ドキュメントは読み進められます。

GraphRAG については、[Microsoft Research の解説（2024-02-13）](https://www.microsoft.com/en-us/research/blog/graphrag-unlocking-llm-discovery-on-narrative-private-data/) が、通常の RAG が弱い問いを 2 つ挙げています — **バラバラの情報を共通の属性でつなぐ問い**と、**データセット全体を俯瞰する問い**（「上位 5 つのテーマは何か」）です。この 2 つが自分の用途に当てはまるかが、グラフを導入する判断材料になります。

## AI エージェントでの使いかた

### 1. エージェントに渡す語彙と制約を定義する

エージェントに「稼働中の設備を止めてよいか」を判断させるには、「稼働中」の定義と、止めてよい条件が要ります。プロンプトに毎回書くのではなく、定義の側に置きます。プロンプトへ詰め込む方式と違い、定義は 1 か所で更新でき、誰が使っても同じ意味になります。

### 2. ナレッジグラフをエージェントの参照先にする

エージェントが推論を始める前に、必要なデータが関係付いた状態で揃っていることが理想です。文書を毎回検索して組み立て直すのではなく、グラフを引きます。関係をたどる問い（「この部品を使っている製品の、出荷先の国は」）は、この形でしか安定して答えられません。

### 3. 統制された層を通して触らせる

**LLM にグラフのクエリをその場で自動生成させる方式には、精度の限界があります。** 実務では、定義を人がガバナンスし、エージェントには統制された層（API・MCP サーバー）を通して問い合わせさせる形が現実的です。後述の 2 つの実装は、いずれもこの設計を採っています。

## 実装を見る 3 つの入口

規模と前提がまるで違う 3 つを並べます。前の 2 つは組織で形式的な定義を作る側、3 つ目は**それを作らずに済ませる側**です。

| | AWS Context Ontology Accelerator | Palantir Foundry Ontology | GBrain |
|---|---|---|---|
| 形態 | ソースを読める OSS（Apache-2.0） | 商用プラットフォームの中核機能 | 個人が公開した OSS（MIT） |
| 位置づけ | 既存データからオントロジーを作る「加速装置」 | データ・ロジック・アクション・権限を統合する運用レイヤー | Markdown を源に知識グラフが自動で組み上がる記憶層 |
| エージェントへの提供 | MCP サーバー / REST API | Ontology が公開するオブジェクト・関数・アクション | MCP（stdio / HTTP）/ CLI |
| `提供元` / `状態` | Official（AWS） / GA（[2026-07-31 公開](https://aws.amazon.com/about-aws/whats-new/2026/07/aws-context--ontology-accelarator-generally-available/)） | Official（Palantir） / GA | Community（個人 OSS） / Experimental |

### AWS Context Ontology Accelerator

[aws/context-ontology-accelerator](https://github.com/aws/context-ontology-accelerator) は、AWS が 2026-07-31 に Apache-2.0 で公開した OSS です。**Scan → Model → Serve** の 3 段階で動きます。

| 段階 | 内容 |
|------|------|
| Scan | データソースに接続し、スキーマを発見してメタデータを補強する。非構造の文書も取り込む |
| Model | AI がオントロジーの草案を作り、統合された意味グラフを構築する |
| Serve | エージェントへ MCP サーバーと REST API で文脈を提供する |

設計上の要点は、**草案は AI が作り、ドメイン専門家が全要素をレビューして承認する**ことが前提に組み込まれている点です。知識グラフは W3C 標準で保持されます。初期リリースは Amazon Neptune（グラフストア）、Amazon OpenSearch Serverless（ベクトルストア）、Amazon Bedrock（基盤モデル）を使います。

> 活発に開発中のため、リポジトリ自身が開発ブランチではなく**タグ付きリリースの使用**を推奨しています。導入時は最新の README を確認してください。

### Palantir Foundry Ontology

[公式ドキュメント](https://www.palantir.com/docs/foundry/ontology/overview)は、Ontology を「組織のデジタルツイン」と定義し、**意味的要素（オブジェクト・プロパティ・リンク）と動的要素（アクション・関数・動的セキュリティ）の両方を含む**としています。単なるセマンティックレイヤーではなく、データ・ロジック・アクション・権限を一体で扱う運用レイヤーという位置づけです。

エージェントは生データではなく、この統制された層の上で動きます。**何を読めて、何を実行できて、誰の権限で動くのか**が層の側で決まる、という設計は、OSS 側の実装を読むときの比較軸としても使えます。

### 形式的な定義を作らない選択肢 — GBrain

[GBrain](https://github.com/garrytan/gbrain) は、Y Combinator の CEO である Garry Tan が 2026 年 4 月に MIT ライセンスで公開した、エージェント向けの知識・記憶層です。**OWL / RDF で語彙を定義する手前で止める**点が、前の 2 つと決定的に違います。

| 観点 | 内容 |
|------|------|
| 知識の置き場所 | 通常の git リポジトリ（brain repo）の **Markdown ファイルが正**。検索用に PGLite または Postgres へ同期する |
| グラフの作りかた | エンティティ参照を抽出して型付きの関係（`works_at` など）を自動で張る。**書き込みごとの LLM 呼び出しがない**ため、広く索引を張ってもコストが跳ねない |
| 2 つの問い方 | `gbrain search` は上位ページを返す（速い・LLM コストなし）。`gbrain think` は根拠付きで統合した答えと、**まだ分かっていないことの指摘**を返す |
| エージェントからの接続 | 大半の操作を MCP ツール（stdio / HTTP）として公開。Claude Code・Codex・Cursor 等から使える |

**`gbrain think` が「まだ分かっていないこと」を返す**設計は、このページの他の実装と同じ方向を向いています。答えられない範囲を答えらしく埋めないことが、統制された知識層の要件だからです。

一方で、これは**単一の担当者が自分の知識を管理する前提**の作りです。組織の共通語彙を全社で合意し、権限つきで運用したい場合は、前の 2 つが対象になります。

> 導入時の注意: **GBrain は npm で配布されていません。** npm 上の同名パッケージは無関係な別物で、入れると PATH 上の正規バイナリを隠してしまいます（[Skill / Plugin のセキュリティ](skill-security.md#5-同名の別パッケージという入口)）。開発は速く、バージョンの動きも大きいため、導入手順は[リポジトリ](https://github.com/garrytan/gbrain)の README を一次情報として確認してください。

## 運用で効いてくること

- **定義を維持する担当を決める** — オントロジーは作って終わりではありません。定義の変更を誰が承認するかが決まっていないと、古い意味のまま参照され続けます。
- **AI が作り、人が承認する** — 草案作成を自動化しても、承認は人が担う。上記 2 つの実装が共通して採っている前提です。
- **エージェントの権限は層の側で決める** — 何を読めて何を実行できるかは、プロンプトではなく提供層で制限します（[Skill / Plugin のセキュリティ](skill-security.md)）。
- **小さく始める** — 全社の意味を一度に定義しようとすると終わりません。用語のゆれが実害を出している 1 領域から始めます。
