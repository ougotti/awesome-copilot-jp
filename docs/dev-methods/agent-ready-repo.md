# エージェントが働きやすいリポジトリ — 渡すコンテキストの設計

> **対象ツール**: ツール横断（Claude Code・Codex・GitHub Copilot ほか AGENTS.md 対応ツール） ｜ **実行環境**: CLI / IDE / Cloud ｜ **対象読者**: リポジトリを管理する開発者・チームのリード ｜ **最終更新**: 2026-10-24

> コーディングエージェントの出来は、モデルだけでなく**リポジトリが何を渡すか**で変わります。指示ファイル（`AGENTS.md`・`CLAUDE.md`・`.github/copilot-instructions.md`）に何を書くか、何を Skill やテスト・CI に移すか、エージェントが自分の変更をどう確かめられるようにするか。このページは、ツールごとのページに散らばっていた指示ファイルの説明を横断して、**設計の判断**をまとめます。各ツールの配置場所の細かい規則は、末尾の関連ドキュメントから各ガイドを参照してください。

---

## 1. 最初に知っておくこと — 指示ファイルは「効く」とは限らない

指示ファイルを置けばエージェントが賢くなる、という前提は一次資料で裏付けられていません。

Gloaguen らの [Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?](https://arxiv.org/abs/2602.11988)（2026-02 初版、2026-09 に v3）は、SWE-bench のタスクと、開発者が実際に指示ファイルをコミットしているリポジトリの課題で、指示ファイルの有無を比べました。要約で報告されている結果は次のとおりです。

| 観点 | 結果 |
|---|---|
| タスクの成功率 | 指示ファイルを与えても**全体としては上がらなかった**。LLM が生成したファイルでも、開発者が書いたファイルでも同じ傾向 |
| 推論の費用 | **平均で 20% 以上増えた** |
| 書かれた指示 | エージェントは**よく守った** |
| リポジトリの概要の説明 | 広く勧められているにもかかわらず、**役に立たなかった** |
| 著者の推奨 | 標準的でないコーディングの慣行を指定する用途には有用。性能の向上を狙うなら、導入前に厳密に評価する |

一方、Vercel は [AGENTS.md outperforms skills in our agent evals](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)（2026-01-27）で、学習データにない Next.js 16 の API を使う課題について、**ドキュメントの索引を `AGENTS.md` に置いた構成が、同じ内容を Skill にした構成より高い合格率**だったと報告しています。既定の Skill は評価ケースの 56% で一度も呼び出されず、明示的に指示すると呼び出されたものの、指示の言い回しで結果が大きく変わりました。

2 つは矛盾しません。読み取れるのは次のことです。

- **モデルがすでに知っていることや、コードを読めば分かることを書いても効かない**（概要の説明・一般的な規約）
- **モデルが知らないこと、コードから読み取れないことは効く**（学習データにない API、標準と違う慣行、手順）
- **書いたものは守られる**ので、間違ったことや古いことを書くと、それも守られる
- **毎回読ませる内容は、毎回費用がかかる**

> **Hacker News での受け止め（コミュニティの見方）**: この 2 つは [論文](https://news.ycombinator.com/item?id=47034087)・[Vercel の記事](https://news.ycombinator.com/item?id=46809708)とも Hacker News で数百点の議論になりました。実務者の経験談として繰り返し出たのは、①ビルド・テストの手順や「なぜこうなっているか」など**コードから読み取れない背景**は効く、②「〜するな」と書くより、機械的に止められるものは lint や pre-commit に移すほうが確実、③問題が起きたときだけ足し、トップレベルは短く保ってサブディレクトリに分ける、という点です。論文には、LLM に生成させたファイルは当たり前のことを書きがちで「良い文書の効果」を測ったものではない、対象が Python と issue の解決に偏っている、という批判もありました。Vercel の評価には、差が小さく試行回数に対して誤差の範囲かもしれないという指摘があります。**どちらの結果も、自分のリポジトリで確かめる前提で読んでください。**

## 2. 各ツールが読む指示ファイル

| ツール | 主な指示ファイル | 読み方 | 詳細 |
|---|---|---|---|
| Claude Code | `CLAUDE.md`（ルート・サブディレクトリ・`~/.claude/`） | 起動時に読み、サブディレクトリのものは配下を扱うときに読む。`CLAUDE.md` がないときだけ `AGENTS.md` を読む（2.1.277 から）。上限を超える入れ子の `CLAUDE.md` は先頭だけ（2.1.309） | [Claude Code](../claude-code/basics.md#claudemd) |
| Codex | `AGENTS.md` | 階層ごとの読み込みと優先の規則は公式ドキュメントで確認する | [Codex ガイド](../codex/README.md) |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/*.instructions.md`（`applyTo` でパスを指定）、`AGENTS.md`（coding agent など） | リポジトリ全体の指示は常に、パス別の指示は該当ファイルを扱うときに効く。CLI でも 1.0.100 からパス別の指示を自動で適用 | [Instructions](../copilot/instructions.md)、[Copilot ガイド](../copilot/README.md#instructions---コーディング規約の自動適用) |
| AGENTS.md 対応ツール全般 | `AGENTS.md`（ルートとサブディレクトリ） | **編集中のファイルに最も近い `AGENTS.md` が優先**し、チャットでの明示の指示がすべてに優先する（[AGENTS.md](https://agents.md/)） | — |

`AGENTS.md` は Linux Foundation の Agentic AI Foundation（AAIF）が管理するオープンな形式で、Codex・Jules・Cursor・Gemini CLI・GitHub Copilot の coding agent など多くのツールが対応しています。**複数のツールを使うチームは、共通の内容を `AGENTS.md` に置き、ツール固有の内容だけを各ツールのファイルに分ける**のが扱いやすい構成です。ただし Claude Code は `CLAUDE.md` があると `AGENTS.md` を読まないため、両方を置くなら `CLAUDE.md` から `AGENTS.md` の内容を参照させるか、一方に寄せてください。

## 3. 何を指示ファイルに書き、何をほかへ移すか

指示ファイルは**毎回読まれ、毎回費用がかかり、書いたことは守られる**場所です。そこに置く価値があるものだけを置きます。

| 内容 | 置き場所 | 理由 |
|---|---|---|
| ビルド・テスト・lint の**コマンド** | 指示ファイル（短く） | エージェントが自分で確かめるための入口。コードから推測させると間違える |
| 標準と違う慣行、「なぜこうなっているか」 | 指示ファイル | コードから読み取れない。研究でも効く側に入る |
| 学習データにない API・社内ライブラリの使い方 | 指示ファイルの**索引**から、詳しい文書へリンク | 全文を毎回読ませると費用がかかる。索引だけを常に置き、本文は必要時に読ませる |
| 特定の作業の手順（移行・リリース・調査） | **Skill** | 利用者が明示的に起動する作業に向く。常に必要ではない |
| 機械的に判定できる禁止事項（書式・依存の制限・秘密情報） | **lint・型検査・pre-commit・CI** | 「〜するな」は破られ得る。止められるものは仕組みで止める（[自然言語の判断と強制する制御を分ける](skill-security.md#自然言語の判断と強制する制御を分ける)） |
| プロジェクトの概要・技術スタックの一般的な説明 | README（人向け） | 研究では効かなかった。エージェントはコードを読めば分かる |
| 権限・実行してよい操作 | 各ツールの設定（permissions・sandbox・managed settings） | 指示ファイルの文章は権限の境界にならない |

**モノレポでは分けて置きます。** ルートの `AGENTS.md` は全体に共通することだけにし、各パッケージの `AGENTS.md`（Claude Code ならサブディレクトリの `CLAUDE.md`、Copilot なら `applyTo` 付きの instructions）に固有の手順を置くと、その場所を扱うときだけ読まれます。

## 4. エージェントが自分で確かめられるようにする

指示ファイルより効果が確かなのは、**エージェントが自分の変更の正しさを確かめる手段**です。[ループエンジニアリング](loop-engineering.md#停止条件の作り方)で言う「機械が判定できる停止条件」を、リポジトリの側に用意します。

| 用意するもの | エージェントにとっての意味 |
|---|---|
| **1 つのコマンドで走るテスト**（例: `npm test`、`make test`） | 変更のたびに確かめられる。手順が複数あると省かれやすい |
| 速いテストと遅いテストの分離 | 速いものを毎回、遅いものを最後に回せる |
| lint・型検査・フォーマッタ | 書式の指示を指示ファイルに書かずに済む |
| 再現手順のある issue テンプレート | 不具合を再現してから直すループを回せる |
| CI の結果を読める状態（ログへのアクセス） | 手元で再現しない失敗も扱える |
| サンプルデータ・テスト用の環境変数（`.env.example`） | 本物の秘密情報を渡さずに動かせる |

テストのないコードは、エージェントにとっても人にとっても**変えてよいかを判断できないコード**です。エージェントを入れる前に、よく変えるところからテストを足すのが近道です（[レガシーのモダナイゼーション](legacy-modernization.md)も同じ考え方）。

## 5. 指示ファイルを保守する

| やること | 方法 |
|---|---|
| **失敗したときに足す** | エージェントが同じ誤りを繰り返したら、その誤りを防ぐ 1 行を足す。最初から網羅しようとしない（[ハーネスエンジニアリング](harness.md#ハーネスエンジニアリングという実践)の考え方） |
| **古くなったものを消す** | パス・コマンド・ライブラリの変更に合わせて直す。Claude Code では `/doctor prompt-audit` が古い記述の候補を挙げる（[evals](evals.md#モデルの更新も変更として扱う--prompt-audit-で点検してから測る)） |
| **効いているかを測る** | 指示を足す前後で、同じ課題を何回か実行して比べる。差が小さいなら、その指示は費用だけを増やしている可能性がある（[evals](evals.md)） |
| **レビューを通す** | 指示ファイルの変更はエージェントの振る舞いを変える変更として、CODEOWNERS でレビューを必須にする（[レビュー指示](review-instructions.md#5-ルールの変更を誰が承認するか)） |
| **生成させたものをそのまま置かない** | `/init` などで生成した雛形は、当たり前のことを消し、コードから読めない背景だけを残してから置く |

## 人が確認すること

- 指示ファイルの各行が「コードから読み取れないこと」か。読めることなら消せないか
- 機械的に判定できる禁止事項が、文章ではなく lint・CI で止められているか
- テストが 1 つのコマンドで走り、エージェントがそれを知っているか
- 複数のツールを使う場合、どのツールがどのファイルを読むかを把握しているか（Claude Code の `CLAUDE.md` 優先に注意）
