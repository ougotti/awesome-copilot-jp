# AIエージェントのID・認可・委任権限

> **対象ツール**: ツール横断（Claude Code・Codex・GitHub Copilot ほか） ｜ **実行環境**: CLI / IDE / Cloud ｜ **対象読者**: エンジニア ｜ **最終更新**: 2026-09-09

> [Skill / Plugin のセキュリティ](skill-security.md)は Skill・Plugin という**導入するモノ**の確認手順を扱います。このページは、常駐・非同期・マルチエージェントで重要になる**エージェント自身をどう認証し、何を委任してよいかという設計判断**を独立して整理します。

---

## 1. なぜ AI エージェントにも固有 ID が必要か

エージェントに人間のパスワードや API キーをそのまま渡す設計は、初期段階では動きます。しかし次の場面で破綻します。

- **誰が実行したか分からない** — ログに残るのは人間のアカウントで、どのエージェント・どのタスクが操作したかを後から特定できない
- **失効の単位が粗い** — 1 つのエージェントを止めたいだけなのに、共有している人間の資格情報全体を失効させるしかない
- **権限の絞り込みができない** — 人間の資格情報はそのアカウントが持つ全権限を引き継ぐため、エージェントに必要な範囲だけを渡せない

米国 NIST は 2026-02-17 に **AI Agent Standards Initiative** を発表し、重点分野の 1 つに「AIエージェントのセキュリティとアイデンティティ」を挙げました。これを受けて NIST の ITL（Information Technology Laboratory）が 2026-02-05 に **AI Agent Identity and Authorization の concept paper** を公開し、意見募集を行っています。**エージェント固有の ID と権限設計**は、業界横断の標準化課題として扱われている段階にあります。

---

## 2. 人間の代理、サービスアカウント、エージェント固有 ID の比較

| 方式 | 誰として実行するか | 失効の単位 | 監査での見え方 |
|------|------------------|-----------|--------------|
| 人間の資格情報を共有 | その人間そのもの | 人間の資格情報ごと（エージェント単位では止められない） | ログ上、人間の操作とエージェントの操作を区別できない |
| サービスアカウント | 部門・システム単位の共有アカウント | サービスアカウントごと（複数エージェントが相乗りしていると影響範囲が広い） | 「どのシステムか」は分かるが「どのエージェント・どのタスクか」は分からない |
| エージェント固有 ID | エージェントそのもの | エージェント単位で個別に失効できる | 誰が・どのエージェントに・何を実行させたかを追跡できる |

**エージェント固有 ID が理想形ですが、必須ではありません。** 小規模な検証段階でサービスアカウントから始めるのは合理的な選択です。ただし「失効の単位」と「監査での見え方」が粗くなることは、その時点で認識しておく必要があります。

---

## 3. 認証／認可／委任／人間の承認の違い

この 4 つを混同すると、設計の議論がすれ違います。

| 用語 | 問いへの答え |
|------|-------------|
| **認証（Authentication）** | このリクエストを送っているのは誰か |
| **認可（Authorization）** | その相手に、この操作を許可するか |
| **委任（Delegation）** | ある主体（親エージェント）が、別の主体（サブエージェント）に自分の権限の一部を渡すこと |
| **人間の承認（Human approval）** | 認証・認可の仕組みを通っていても、実行前に人間の判断を挟むかどうか |

**委任は「トークンを渡すこと」ではありません。** 子が親の権限をそのまま引き継ぐのか、それより狭い権限（attenuated）に絞って引き継ぐのかを決め、**子が親の代理として動いたことを記録する**ことが委任の本体です。「権限を渡した」で終わらせず、「どこまで渡したか」「誰の代理として動いたか」を残す設計が必要です。

**→ MCP・A2A それぞれの認証・認可の位置づけは [MCP と A2A — 役割の違いと併用方法](agent-protocols.md) を参照**

## 4. OAuth scope、token audience、短寿命 token、失効

[MCP の Authorization 仕様](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)と[Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)は、エージェントの権限設計に直結する原則を定義しています。

| 原則 | 内容 |
|------|------|
| **scope の最小化** | `scopes_supported` に全権限を並べない。まず低リスクな読み取りだけの最小スコープで始め、必要になった操作だけを都度昇格させる（`insufficient_scope` エラーで追加スコープを要求する） |
| **token audience の検証** | サーバーは「自分宛てに発行された token か」を検証する。audience を検証せず、他サービス向けの token を受理してはならない |
| **token passthrough の禁止** | MCP サーバーは、クライアントから受け取った token をそのまま下流の API へ転送してはならない（**明示的に禁止**）。転送するとレート制限や監査などの下流の制御をすべて回避でき、後から「どのクライアントが実行したか」を区別できなくなる |
| **短寿命 token** | 認可サーバーは token を短寿命にすることが推奨される。漏洩した token の影響範囲を、有効期限で限定する |
| **failure の扱い** | audience 不一致・期限切れの token は拒否する（401）。scope 不足は 403 で、必要な scope を明示して返す |

これらは「クライアント（エージェント）とサーバー（ツール）の間」の話です。エージェント同士の委任（次節）では、これに加えて「誰の代理として動いているか」を扱う必要があります。

## 5. 親エージェントからサブエージェントへ渡してよい権限

サブエージェントへの委任で最も見落とされるのが、**権限の増幅**です。親エージェントが持つ権限をそのままサブエージェントに渡すと、サブエージェント側の実装ミスやプロンプトインジェクションが、親と同じ範囲の被害を生みます。

| パターン | 権限の渡し方 |
|---------|-------------|
| 単一エージェント | 権限の伝播なし。1 つの認可の範囲で完結する |
| サブエージェント（プロセス内） | 親が持つ権限の**部分集合**だけを渡す。タスクに必要な最小のスコープに絞る |
| A2A（エージェント間） | Agent Card が公開する能力の範囲でしか委任できない。相手が信頼できない場合、渡す権限はさらに狭める |

**判断基準は「このサブエージェントの担当作業に、渡そうとしている権限は本当に必要か」です。** 親が持つ権限をまるごと渡すのはデフォルトの選択にせず、都度絞り込みます。

**→ 単一・サブエージェント・マルチエージェントの構成そのものをいつ選ぶかは [マルチエージェントを使う境界線](multi-agent.md) を参照**

## 6. 所有者、実行主体、承認者、監査者の責任分界

権限の設計と、責任の所在は別の軸です。最低限、次の 4 者を分けて考えます。

| 役割 | 誰が担うか | 問い |
|------|-----------|------|
| **所有者（Owner）** | エージェントを動かすことを決めた人・チーム | このエージェントの存在に責任を持つのは誰か |
| **実行主体（Actor）** | エージェント固有 ID、またはそれに準ずる識別子 | 実際にリクエストを送ったのはどの ID か |
| **承認者（Approver）** | 不可逆な操作の実行前承認を行う人 | この操作を実行してよいと判断したのは誰か |
| **監査者（Auditor）** | ログ・記録を事後に確認する人・チーム | 何が起きたかを後から検証できるか |

同一人物が複数の役割を兼ねること自体は問題ではありません。**問題は、この 4 つを区別せずに「エージェントが勝手にやった」で済ませてしまうことです。** 実行主体が明確な ID を持っていれば、少なくとも「どのエージェントが」までは特定できます。

## 7. control plane が担う inventory・policy・telemetry・kill switch

組織でエージェントの数が増えると、個々のエージェントの設定だけでは管理できなくなります。[ハーネス](harness.md)の上位、あるいはハーネスの一部として、次の機能を持つ **control plane** が必要になります。

| 機能 | 何をするか |
|------|-----------|
| **inventory** | 組織内にどのエージェントが存在し、それぞれ何の ID で動いているかを一覧できる |
| **policy** | どのエージェントにどの scope・どの MCP サーバー・どの Plugin を許可するかを、個々の設定ではなく中央で管理する（[Skill / Plugin のセキュリティ 4 節](skill-security.md#4-組織で許可範囲を絞る)の MCP allowlists / `managed-settings.json` はこの一部） |
| **telemetry** | 各エージェントの実行ログを収集し、異常な挙動を検知できる |
| **kill switch** | 個別のエージェント ID を即時に停止・失効できる（人間の資格情報全体を止める必要がない） |

これは[AI エージェントの実行基盤（ハーネス）](harness.md)が「認証、スコープ、権限、配送、cron、監査、永続化」を引き受ける層として説明している内容と同じ層です。エージェント ID・権限の設計は、この control plane に何を管理させるかを決める前提になります。

---

## 8. 最小構成チェックリスト

導入時に、少なくとも次を満たしているかを確認します。

- [ ] エージェントは、人間の資格情報を直接共有していない（サービスアカウント以上の分離がある）
- [ ] scope は必要最小限から始まり、必要になった操作だけ昇格する設計になっている
- [ ] token の audience が検証されており、他サービス向けの token を受理しない
- [ ] MCP サーバーが、受け取った token を下流へそのまま転送していない（token passthrough になっていない）
- [ ] サブエージェントへ渡す権限は、親の権限の部分集合に絞られている
- [ ] 不可逆な操作には、実行前の人間承認が入っている
- [ ] 所有者・実行主体・承認者・監査者を後から区別できるログが残る
- [ ] 個別のエージェント ID を即時に停止できる（kill switch がある）
