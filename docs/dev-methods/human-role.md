# 人の仕事はどこに移るか — レビューが律速になるとき

> **対象ツール**: ツール横断 ｜ **実行環境**: — ｜ **対象読者**: 開発チームのリード・エンジニアリングマネージャー・エージェントと働く開発者 ｜ **最終更新**: 2026-10-24

> コーディングエージェントで「書く」速さは上がりました。その結果、チームの流れの中で詰まる場所が**書く工程から、変更を信頼してよいか判断する工程**へ移りつつあります。このページは、確認できた研究が示す傾向と限界を整理し、律速がレビューに移ったときの対策と、人が持ち続ける仕事、経験の浅い開発者の育成についての考え方をまとめます。AI レビュアーの精度の測り方は [AI 時代のコードレビュー](ai-code-review.md)、導入効果の測り方は [AI 導入の効果をどう測るか](ai-adoption-metrics.md) を参照してください。

> [!NOTE]
> このテーマの研究の多くは**査読前のプレプリント**で、公開されたオープンソースのリポジトリの観察です。組織の非公開のコードや、新しいモデルの版にそのまま当てはまるとは限りません。本ページは、一次資料で確認できた数値だけを、対象と限界を併記して書きます。販売元のブログの数値は使いません。

## 1. 研究が示している傾向

| 研究 | 対象 | 確認できた結果 | 限界 |
|---|---|---|---|
| Robbes ら [Agentic Much? Adoption of Coding Agents on GitHub](https://arxiv.org/abs/2601.18341)（2026-01、v2 は 2026-04、プレプリント） | 約 12 万 8 千の GitHub プロジェクト | 2026-02 時点の推定採用率は **22.20〜28.66%**。成熟したプロジェクトや大きな組織にも広がる。エージェントが支援したコミットは**人だけのコミットより大きい** | エージェントが残す痕跡で判定するため、痕跡を残さない使い方は数えられない |
| Popescu ら（Delft 工科大学・UC Davis・GitHub）[Investigating Autonomous Agent Contributions in the Wild](https://arxiv.org/abs/2604.00917)（2026-04、プレプリント） | 約 11 万件のオープンソースの PR。Codex・Claude Code・Copilot・Jules・Devin と人の PR を比較 | エージェントの PR は**大きく**（Claude Code の中央値は 376 行、人は約 60 行）、追加が中心。マージ率は人より高いものもあるが、**マージ後のコードは人のコードより書き換え・削除されやすい** | エージェントの PR は星の少ないリポジトリに多く、依頼した本人がマージしている可能性がある。外部のレビューが緩い環境の結果かもしれない |
| Kraishan [Not All Agents Are Equal](https://arxiv.org/html/2609.17598)（2026-09、プレプリント） | エージェントの PR のマージ後 90 日 | revert・churn・レビューの負荷はエージェントごとに差がある | 割り当てがランダムでなく、タスクの難しさ・PR の大きさが交絡する。詳細は [evals](evals.md) |
| Crane・Soto [AI and Coder Employment: Compiling the Evidence](https://www.federalreserve.gov/econres/feds/ai-and-coder-employment-compiling-the-evidence.htm)（FEDS 2026-018、2026-03） | 米国のプログラマーの雇用 | ChatGPT の登場後、プログラマーの雇用の伸びが**急に鈍った**。業界ごとの要因では説明しきれない | 職種に固有の変化を「示唆する」にとどまり、LLM が原因とは断定していない。予備的な研究で、FRB の公式見解ではない |

読み取れることは次の 3 点です。

1. **1 回の変更が大きくなっている。** 大きな PR は読むのに時間がかかり、読み飛ばされやすい
2. **マージされることと、残ることは違う。** マージ率が高くても、後から書き換えられる割合が高ければ、手戻りが後ろに移っただけ
3. **観察の環境が、レビューの緩い側に偏っている。** 厳しくレビューする組織で同じ結果になるかは分かっていない

> **Hacker News での受け止め（コミュニティの見方）**: [Ask HN: Do you have any evidence that agentic coding works?](https://news.ycombinator.com/item?id=46691243)（2026-01、450 件以上のコメント）では、うまくいった条件として**範囲が明確な定型作業**（ボイラープレート・小さなツール・言語の移植）と**結果を機械的に確かめられる作業**、うまくいかなかった条件として**大きく複雑なコードベースと設計判断**が繰り返し挙がりました。「書くのは一度だが、レビューは PR ごとにかかり続ける」「経験の浅い人は出力の良し悪しを見分けにくい」という指摘も多く見られます。経験談であり統計ではありませんが、研究の傾向と同じ方向を向いています。

## 2. 律速がレビューに移る理由

| 理由 | 何が起きるか |
|---|---|
| **書く速さと読む速さの差** | エージェントは数分で数百行を書くが、人が責任を持って読める量は増えない |
| **意図が残らない** | エージェントが検討して捨てた案や判断の理由は、差分を作った後に消えることが多い。レビュアーは意図を後から推測するしかない |
| **大きな PR** | 一度に多くを変えるため、どこが本質的な変更か見分けにくい |
| **テストの書き換え** | テストごと変えると、CI は通っても正しさの基準が動く（[AI 時代のコードレビュー](ai-code-review.md#1-実装と正しさの基準を分ける)） |
| **レビュアーの数は増えない** | 書き手（エージェント）は増やせても、マージの責任を持てる人は増えない |

## 3. 対策の選択肢

どれか 1 つではなく、組み合わせて使います。

| 対策 | やること | 関連 |
|---|---|---|
| **変更を小さく保つ** | 1 つの PR に 1 つの目的。目的と検証の結果が書かれていない大きな PR は受け付けない | [ループエンジニアリング](loop-engineering.md) |
| **リスクで分ける** | 認証・決済・データ削除・権限など影響の大きい箇所だけ人の時間を厚く使い、影響の小さい変更は AI のレビューと自動の検査に任せる | [エージェントに外部操作を与える手段の選び方](tool-selection.md#8-承認境界--読み取り入力送信購入削除で分ける)と同じ分類の考え方 |
| **仕様と受け入れ条件を先に決める** | 「何をもって完了か」を変更の前に書く。レビューは条件を満たすかの確認になり、意図の推測が減る | [仕様駆動開発](spec-driven.md)、[`/goal` の完了条件](agent-commands.md#goal-には修正内容と完了条件を書く) |
| **意図を残させる** | エージェントに、目的・検討して捨てた案・検証した方法を PR の説明に書かせる | — |
| **AI のレビューを一次の読み手にする** | 機械的に見つかる問題は AI に先に指摘させ、人は「この変更を作るべきか」「仕様にない振る舞いがないか」を見る。AI の指摘は判断材料で、マージの責任は人が持つ | [AI 時代のコードレビュー](ai-code-review.md)、[レビュー指示](review-instructions.md) |
| **基準を緩めない** | テストの書き換えを重点的に見る。CI の基準を、通すために下げない | [AI 時代のコードレビュー](ai-code-review.md#テストの変更のチェックリスト) |

## 4. 人が持ち続ける仕事

エージェントに任せられるのは**作業**で、**判断と説明責任**ではありません。[ループエンジニアリング](loop-engineering.md#落とし穴)で引いた「内側のループはエージェント、外側のループは人」という切り分けと同じです。

| 人の仕事 | 内容 |
|---|---|
| **何を作るかを決める** | 解く問題・作らないもの・優先順位 |
| **意図を検証する** | 変更が、決めた目的と条件を満たしているか。仕様にない振る舞いが混ざっていないか |
| **リスクを引き受ける** | どの変更を人が見るかの線引きと、マージの判断 |
| **説明できる状態を保つ** | 出荷したコードについて、なぜそうなっているかを説明できること。読んでいないコードを「済み」にしない（[理解の負債](loop-engineering.md#落とし穴)） |
| **仕組みを直す** | エージェントが同じ誤りを繰り返したら、指示・テスト・検査を足す（[ハーネスエンジニアリング](harness.md#ハーネスエンジニアリングという実践)、[エージェントが働きやすいリポジトリ](agent-ready-repo.md)） |

## 5. 経験の浅い開発者の育成

経験の浅い開発者への影響を切り分けた研究は、確認できた範囲ではまだ少数です（雇用の統計は上の FEDS の研究のように全体の傾向にとどまります）。以下は根拠の強さが違う考え方を分けて並べたものです。

| 考え方 | 根拠の種類 |
|---|---|
| 出力の良し悪しを見分ける力は、自分で書いて直した経験から育つ。最初から生成に頼ると、見分ける力が育ちにくい | 実務者の議論（上の Ask HN など） |
| 設計と仕様を人が持ち、エージェントを実行役として使うと、経験の浅い人でも効果を得やすい | 実務者の議論 |
| エージェントへの依頼の仕方（計画・完了条件・検証の渡し方）そのものが、身につけるべき技能になる | 実務者の議論、METR が指摘した「使い方で取り組むタスクが変わる」点（[効果の測り方](ai-adoption-metrics.md#metr--体感と実測がずれる)） |

チームでの運用としては、本ガイドでは次を設計例として勧めます。

- 経験の浅い人の PR では、**エージェントの出力を自分の言葉で説明する**ことを求める（説明できない部分は書き直す）
- レビューする側に回る機会を作る。**他人のエージェントの PR を読む**ことは、見分ける力を育てる練習になる
- テストと受け入れ条件を先に書く練習を、エージェントを使う作業の中に組み込む

## 人が確認すること

- チームの流れのどこで待ちが増えているか（レビュー待ち・CI 待ち・マージ後の手戻り）を見ているか
- 大きな PR を、目的と検証の結果つきで小さく分けさせているか
- 人が見る変更と AI に任せる変更の線引きが、文書になっているか
- 研究の数値を引用するとき、プレプリントであることと対象の偏りを併記しているか
