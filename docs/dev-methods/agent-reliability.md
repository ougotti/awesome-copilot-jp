# 長時間タスクの信頼性設計

> **対象ツール**: ツール横断（Claude Code・MCP・LangGraph ほか） ｜ **実行環境**: CLI / Cloud ｜ **対象読者**: エンジニア ｜ **最終更新**: 2026-09-09

> [ループエンジニアリング](loop-engineering.md)はエージェントを反復実行する方法と停止条件を、[AI エージェントの実行基盤（ハーネス）](harness.md)は実行環境を扱います。このページはその間にある、**長時間・多段階の仕事で小さな失敗が累積する問題**と、それを抑える信頼性設計を扱います。評価ツールや telemetry の網羅ではなく、**実行中の故障を前提にした** checkpoint・再開・冪等性・検証・reliability budget が対象です。

---

## 1. 「長く動ける」と「長い仕事を正しく完了できる」の違い

METR の **time horizon**（人間専門家がそのタスクを完了するのにかかる時間で、AI にとっての難易度を測る指標）は、しばしば「AI が連続稼働できる時間」と混同されます。METR 自身がこの混同を明示的に否定しています。

> the 50%-time horizon is the length of task in our suite... rather than the time an AI spends to complete the task

> AI agents are typically several times faster than humans on tasks they complete successfully

**time horizon が測っているのはタスクの難易度**であり、エージェントが実際に何時間稼働し続けたかではありません。「長時間動かせるようになった」ことと「長く複雑なタスクを正しく完了できる」ことは別の主張です。このページが扱うのは後者、**難易度の高い長時間タスクを、失敗を前提にどう完了させるか**です。

---

## 2. ステップ数が増えると失敗が累積する理由

各ステップの成功率が 99% でも、100 ステップ連続で成功する確率は 0.99^100 ≈ 37% まで落ちます。**個々のステップの精度だけを上げても、ステップ数が増えれば全体の成功率は下がり続けます。**

長時間タスクの信頼性設計は、この前提から始まります。「失敗をゼロにする」ことを目標にせず、**失敗を検出し、局所化し、再開できる**ことを目標にします。

---

## 3. タスク分割と checkpoint 境界

長いタスクを 1 つの不可分な実行として扱うと、途中で失敗したときに最初からやり直すしかなくなります。**checkpoint を挟める単位にタスクを分割する**ことが、再開可能性の前提です。

分割の目安は「その時点までの結果を、外部から検証できるか」です。検証できない粒度で区切っても、checkpoint が実質的に機能しません（[6 節](#6-中間成果物と終了条件の検証)）。

MCP の **Tasks**（2025-11-25 版仕様、experimental）は、この考え方をプロトコルレベルで実装した例です。

> Tasks are durable state machines that carry information about the underlying execution state of the request they wrap, and are intended for requestor polling and deferred result retrieval.

タスクは常に `working` から始まり、一意な `taskId` を持つ状態機械として管理されます。そこから直接 `completed` / `failed` / `cancelled`（終了状態）へ遷移するのが基本ですが、受信側が追加入力を必要とする場合に限り、`input_required` という**任意の中間状態**を経由できます（`input_required` から `working` へ戻ることも、そのまま終了状態へ進むこともできます）。**この「状態を持つ実行単位として扱う」という発想が、checkpoint 境界の設計そのものです。**

---

## 4. retry、timeout、backoff、fallback

| 要素 | 設計する内容 |
|------|-------------|
| **retry** | 失敗したステップだけを再試行する。全体をやり直さない |
| **timeout** | ステップごとに上限を設ける。応答がないまま待ち続けない |
| **backoff** | 再試行の間隔を広げる（指数バックオフ等）。障害中の相手へ再試行を集中させない |
| **fallback** | 再試行しても解決しない場合の代替手段、または人間への引き継ぎ |

**これらは「エラーを消す」ためではなく、「エラーの種類を切り分ける」ために設計します。** 一時的な障害（retry で解決する）と、恒久的な失敗（fallback が必要）を同じ扱いにすると、無限に再試行し続けるループや、諦めるべきでない場面で早々に諦めるループになります。

MCP Tasks の TTL（`ttl`）も、この設計の一部です。**タスクの保持期限を明示し、期限が切れれば破棄してよい**という前提を置くことで、リソースが無制限に積み上がることを防ぎます。

---

## 5. 冪等性、重複実行、外部副作用の扱い

retry・再開のいずれも、**同じ操作が 2 回実行される可能性**を生みます。特に外部への副作用（メール送信・決済・リソース作成・外部 API 呼び出し）を伴うステップでは、これが実害になります。

- **冪等キー** — 同じ操作に一意な識別子を持たせ、サーバー側で重複を検出・無視できるようにする
- **副作用の位置を分離する** — 「判断・計画」のステップと「実際に外部へ影響を与える」ステップを分け、後者だけを慎重に扱う
- **再試行してよい操作とダメな操作を分ける** — 読み取りは何度再試行してもよいが、送信・購入・削除は違う（[エージェントに外部操作を与える手段の選び方「承認境界」](tool-selection.md#8-承認境界--読み取り入力送信購入削除で分ける)と同じ分類軸）

**再開・retry を実装する前に、「このステップは 2 回実行されても安全か」を必ず確認してください。** 安全でない場合は、冪等性を持たせるか、そのステップの前後に人間の確認を挟みます。

---

## 6. 中間成果物と終了条件の検証

エージェントが「完了しました」と自己申告することと、実際に完了していることは別です（[エージェントに外部操作を与える手段の選び方「方式ごとのテストと完了確認」](tool-selection.md#9-方式ごとのテストと完了確認)と同じ原則）。

長時間タスクでは、これがさらに重要になります。長い実行の途中で生成された中間成果物が、後続のステップの入力として使われ続けるためです。**中間成果物を検証せずに進めると、誤りが後続のステップへ伝播し、最後にまとめて失敗が発覚します。**

- 各 checkpoint で、その時点までの成果物が期待した形式・内容かを機械的に検証する
- 「完了報告」と「成果物の検証」を分離する。報告を検証の代わりにしない
- 検証に失敗した checkpoint からは、その前の正常な checkpoint へ戻ってやり直す（[7 節](#7-pause--resume--cancel--rollback)）

---

## 7. pause / resume / cancel / rollback

長時間タスクは、開始したら完了まで止められない設計にしてはいけません。

| 操作 | 何を可能にするか |
|------|-----------------|
| **pause** | 人間の判断が必要な時点で、実行を一時停止する |
| **resume** | 直前の checkpoint から再開する。最初からやり直さない |
| **cancel** | 実行を打ち切る。MCP Tasks の `tasks/cancel` は、実行中のタスクを `cancelled` 状態へ遷移させる操作として定義されている（**終了状態からは遷移しない**という制約も明示されている） |
| **rollback** | 副作用を伴う操作まで進んでいた場合、それを取り消す、または補償する |

MCP Tasks の仕様は、キャンセル済みタスクの再利用について明確な制約を置いています。

> Once a task is cancelled, it MUST remain in cancelled status even if execution continues to completion or fails.

**「キャンセルした」という状態遷移そのものが、後から覆らない事実として扱われます。** これは長時間タスクの信頼性設計に共通する考え方です。取り消しは「なかったことにする」のではなく、「取り消したという事実を記録する」操作として設計してください。

---

## 8. reliability budget と段階的な人間承認

すべてのステップに同じ厳格さで人間の承認を要求すると、長時間タスクの利点（人がいない間も進む）が失われます。逆に、すべてを無人で進めると、[2 節](#2-ステップ数が増えると失敗が累積する理由)の確率的な失敗の累積がそのまま実害になります。

**reliability budget**は、この間を取る考え方です。

- 読み取り専用・可逆な操作には、広い自律性を与える
- 不可逆な操作・外部への副作用を伴う操作には、承認を挟む（[エージェントに外部操作を与える手段の選び方](tool-selection.md)の承認境界と同じ軸）
- 失敗の累積が一定の閾値を超えたら、無人での継続を止めて人間へ引き継ぐ

Anthropic の実利用データは、経験を積んだ利用者ほど「操作ごとの承認」から**監視・介入型**の運用へ移行する傾向を報告しています。これは、reliability budget を「最初は狭く、実績に応じて広げる」形で運用している例と読めます。**信頼性の設計は一度決めて終わりではなく、実績に応じて調整する対象です。**

---

## 9. 最小テストシナリオ

長時間タスクの信頼性は、正常系だけでは検証できません。最低限、次のシナリオを試してください。

- [ ] 途中の任意のステップで強制的に失敗させ、正しい checkpoint から再開できるか
- [ ] 同じステップを 2 回実行させ、副作用が重複しないか（冪等性の確認）
- [ ] 実行中に cancel し、中途半端な状態が残らないか
- [ ] 中間成果物を意図的に壊し、後続のステップがそれを検出できるか（検証をすり抜けないか）
- [ ] reliability budget の閾値に達した際、実際に人間へ引き継がれるか
