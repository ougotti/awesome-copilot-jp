# 作業中のエージェントへの指示の出し分け

> **対象ツール**: ツール横断（Claude Code・Codex CLI・GitHub Copilot CLI） ｜ **実行環境**: CLI（ターミナル） ｜ **対象読者**: エンジニア ｜ **最終更新**: 2026-09-28

> コーディングエージェントに長い作業を任せると、途中で「条件を足したい」「次にこれも頼みたい」「今の変更の理由だけ聞きたい」という場面が必ず出てきます。3 つとも同じ入力欄に打ち込めますが、**どこへ届くか**はキー操作とコマンドで変わります。このページでは、実行中の追加指示（steer / queue）、作業を汚さない質問（サイドチャット / `/btw`）、完了条件を固定する `/goal` を、3 ツール共通の考え方と各ツールの差分に分けて整理します。
>
> 構成は、nwiizo 氏の記事 [Codexを使うなら、/goalとサイドチャットを押さえておきたい](https://syu-m-5151.hatenablog.com/entry/2026/09/27/120017)（2026-09-27）を出発点にしています。Codex 向けの原典の考え方を、Claude Code と Copilot CLI にも当てはめ、2026-09-28 に各社の公式文書で仕様を確認しました。

> [!IMPORTANT]
> **キーの意味はツールごとに違います。** 特に `Enter` と `Ctrl+Enter` は、ツールによって「今の作業へ割り込む」と「次のターンへ回す」が逆になります。キー操作とコマンドは更新が速いため、表は 2026-09-28 時点のスナップショットです。実際に使えるものは各ツールの `/help` と、末尾の公式リファレンスで確認してください。

---

## 最初に決める — 送る文章は 3 種類ある

作業中に打ち込みたくなる文章は、届け先で 3 つに分けられます。キーを押す前に、どれに当たるかを決めてください。

| 種類 | 届け先 | 典型例 | 間違えると |
|------|-------|-------|-----------|
| **今の作業を変える条件**（steer） | 実行中のターン | 「既存のエラー応答の形式は変えないで」「そのファイルは触らないで」 | 次のターンに回ると、条件に反した変更が先に終わってしまう |
| **次にやってほしいこと**（queue） | 今のターンが終わった後 | 「終わったら README の該当箇所も直して」「次に lint を回して」 | 今のターンに混ざると、作業範囲が広がって途中の判断がぶれる |
| **作業とは別の質問**（サイドチャット） | 主会話の外 | 「この境界値で失敗する理由を説明して」「さっきの用語の意味は」 | 主会話に入ると、説明のやり取りが作業の文脈を押し流す |

迷ったときの目安は「**この文章で、今動いている変更の中身が変わるか**」です。変わるなら steer、変わらないが後で必要なら queue、作業に影響させたくないならサイドチャットです。

## ツールごとのキーとコマンド

2026-09-28 に公式文書で確認した対応です。

| 操作 | Claude Code | Codex CLI | GitHub Copilot CLI |
|------|-------------|-----------|--------------------|
| 実行中に `Enter` | **キューに入る**。ツール呼び出しの切れ目で同じターン内に渡される | **今のターンへ割り込む**（steer） | **今のタスクへの steer** として扱われる |
| 次のターンへ回す | 同じ `Enter`（ターン終了時に残っていれば順に送られる）。コマンドと `!` はターン終了後に実行 | 実行中に `Tab` | 実行中に `Ctrl+Enter` または `Ctrl+Q` |
| 待たずに今送る | `Ctrl+Enter`（または `Ctrl+X Ctrl+S`）。v2.1.275 以降 | —（`Enter` がこれに当たる） | —（`Enter` がこれに当たる） |
| キューを取り消す | 入力欄の先頭行で `↑` を押すと入力欄へ戻る | — | 空の入力欄で `↑` を押すと直近のキュー / steer が入力欄へ戻る。キューは個別に取り消せる |
| サイドチャット | `/btw 質問` | `/side`（別名 `/btw`） | `/ask 質問`（別名 `/btw`） |
| 完了条件を固定して続けさせる | `/goal 条件` | `/goal 目的` | `/goal 目的`（`/autopilot` の別名） |
| 会話を分岐する | `/branch`（手元で分岐）、`/fork`（バックグラウンドの別セッションへ複製） | `/fork` | `/fork`（別名 `/branch`） |
| 前の時点へ戻る | `Esc` 2 回 / `/rewind` | 入力欄が空の状態で `Esc` 2 回（前の発言を編集し、そこから分岐） | `/rewind`（別名 `/undo`） |

読み取るべき点は 2 つです。

- **`Ctrl+Enter` の意味が逆になります。** Copilot CLI では「次のターンへ回す」、Claude Code では「キューを待たずに今送る」です。ツールを行き来する人は、片方の癖でもう片方を操作すると意図と逆の届き方になります。
- **Claude Code の `Enter` は「キュー」ですが、次のターン送りとは限りません。** ツール呼び出しの切れ目で同じターン内に渡されるため、実質的には steer に近い届き方をします。「このターンでは絶対に触れないでほしい」話は、ターンが終わってから送ってください。

## 実行中に送るときの注意

実行中の追加指示は便利ですが、「言った」ことと「反映された」ことは別です。

| 注意点 | 理由 | 対処 |
|-------|------|------|
| **1 回に 1 つの条件だけ送る** | 複数の条件を一度に足すと、どれが反映されたか後で追えない | 条件ごとに分けて送り、反映を確かめてから次を送る |
| **条件は「何を変えないか」まで書く** | 「ついでに直して」は範囲が広がる方向にしか働かない | 「A は変えずに B だけ」の形にする |
| **反映を差分で確かめる** | エージェントの「対応しました」は反映の証拠ではない | `git diff` やテスト結果で、条件どおりの変更になっているか見る |
| **方針自体が間違っているなら止める** | 途中の steer で大きく方向転換すると、前半の変更が残ったまま進む | `Esc` で止め、巻き戻し（上表）で前の時点へ戻してから指示し直す |

## サイドチャットで「説明を聞く場所」を分ける

「なぜこの修正なのか」を主会話で聞くと、説明のやり取りが作業の文脈に積もり、以降の判断がその説明に引っ張られます。説明は主会話の外で聞くのが基本です。

### 3 ツールの違い

同じ「サイドチャット」でも、見える範囲とできることが違います。

| 観点 | Claude Code `/btw` | Codex CLI `/side` | Copilot CLI `/ask`・`/btw` |
|------|--------------------|-------------------|---------------------------|
| 見える文脈 | それまでの会話全体（読んだコード・ツール結果を含む）。書きかけの応答は除く | 主会話から分岐した一時的な会話（ephemeral fork） | 利用できる場合は現在の会話 |
| ツール | **使えない**（ファイル読み取り・コマンド実行・検索をしない） | 公式文書に制限の記述なし | **使えない** |
| 続けて質問 | 1 問 1 答。続けるなら再度 `/btw`（直近 20 件のやり取りは次の質問にも渡る） | サイドチャット内で続けられ、終わったら主会話へ戻る | 1 問 1 答。続けるなら再度 `/ask` |
| 主会話の実行中に使えるか | 使える（主会話を止めない） | 使える（主会話の状態表示は残る） | 使える |
| 主会話の履歴に残るか | 残らない | 残らない（別の会話記録） | 残らない |
| 制約 | ツールが必要になったら `f` で履歴を引き継いだサブエージェントへ分岐（ローカルのみ） | サイドチャット内とレビューモード中は使えない | リモートセッションでは使えない |

ツールを使えない Claude Code と Copilot CLI のサイドチャットは、**すでに会話に出てきた情報からしか答えられません**。まだ読んでいないファイルについて聞くと、推測で答える可能性があります。一方 Codex の `/side` は、公式文書にツール制限の記述がありません。説明だけが欲しいときは、依頼文で変更を禁じてください。

```text
/side 期限切れセッションの判定で、境界時刻の前後で結果が変わる理由を説明してください。コードは変更しないでください。
```

（Codex CLI の入力欄で実行）

### 説明を聞いたら、条件を変えて確かめる

説明に納得したことと、自分が判断できる状態になったことは別です。サイドチャットでは「なるほど」で終わらせず、条件を変えた問いを続けます。

- 「境界時刻がちょうど一致したら、今のコードはどちらに倒れますか」
- 「タイムゾーンが違うサーバーで動かしたら、結果は変わりますか」
- 「その答えを確かめるには、どのテストを追加すればよいですか」

最後の問いへの答えが、次に主会話へ渡す材料になります。

### サイドチャットで決めたことを主会話へ戻す

サイドチャットの内容は主会話の履歴に残りません。決まった仕様は、**人が要約して主会話へ送り直す**必要があります。送り直すときは、説明の経緯ではなく結論と確認方法だけを書きます。

```text
境界時刻と一致したセッションは期限切れとして扱う。境界の直前・一致・直後の 3 ケースを再現テストに加え、一致のケースが失敗することを先に確認してから修正して。
```

（主会話の入力欄で実行。今のターンに反映させたいなら steer、今のターンが終わってからでよいなら queue で送る）

## `/goal` には修正内容と完了条件を書く

`/goal` は、目的を会話に固定し、人が毎回「続けて」と打たなくても作業を続けさせる機能です。3 ツールとも同じ名前のコマンドがありますが、**何をもって完了とするかの判定方法**が違います。

### 3 ツールの違い

| 観点 | Claude Code | Codex CLI | Copilot CLI |
|------|-------------|-----------|-------------|
| 位置づけ | 完了条件を毎ターン判定するループ | 会話に目的を固定する | autopilot モードの開始（`/autopilot` の別名） |
| 完了の判定 | ターンごとに**別の小型モデル**（既定は Haiku）が会話を読み、未達 / 達成 / 不可能を判定する。判定役はツールを使わず、会話に出た証拠だけを見る | ファイル・テスト・ログ等の**具体的な証拠**で確かめてから完了とする方針（公式 cookbook） | エージェント自身がタスク完了と判断するまで続ける |
| 止まる条件 | 達成・不可能の判定、利用者が直す必要のあるエラー、`/goal clear` | `/goal pause` / `/goal clear` | 完了、進めなくなった、`Ctrl+C`、継続回数の上限、AI credit の上限（`--max-ai-credits`） |
| 操作 | `/goal`（状態表示）、`/goal clear` | `/goal`（表示）、`/goal edit`、`/goal pause`、`/goal resume`、`/goal clear` | `/goal on` / `off`、`--max-ai-credits N`、`Shift+Tab` でモード切り替え |
| 権限 | `/goal` は権限モードを変えない。無人で回すなら auto mode と組み合わせる | 公式文書に記述なし。`/permissions` で現在の承認設定を確かめてから使う | 全権限を付与するかを選ぶ画面が出る。制限付きで続けると、承認の要る操作は自動で拒否される |
| 文字数 | 4,000 文字まで | 4,000 文字まで。長い指示はファイルに書いて参照させる | — |

Copilot CLI の継続回数の上限は、概念説明のページでは「既定で 5 回の自動継続で一時停止」、コマンドリファレンスでは `--max-autopilot-continues` の既定を「無制限」と書いており、**2026-09-28 時点で公式文書間の記述が食い違っています**。無人で回すときは `--max-autopilot-continues` と `--max-ai-credits` を明示してください。

### 完了条件（Done When）を先に決める

完了条件が曖昧なまま `/goal` を使うと、エージェントは「それらしく終わった」時点で止まるか、止まらずに作業を広げ続けます。書く前に、次の 4 つを埋めてください。OpenAI の cookbook が挙げる要素と、Claude Code の公式文書が挙げる要素をまとめたものです。

| 要素 | 書くこと | 例 |
|------|---------|-----|
| **終了状態** | 完了したときに成り立っている状態 | 期限切れセッションが拒否される |
| **確かめ方** | それを証明するテスト・コマンド・出力 | 境界の直前・一致・直後の再現テストが成功する |
| **守る条件** | 途中で変えてはいけないもの | 有効なセッションの動作と、既存のエラー応答の形式は変えない |
| **止まり方** | 進めなくなったときに何を報告して止まるか | 再現できない場合は、試したことと必要な情報を報告して止まる |

原典の例を、この 4 要素で書くと次のようになります。

```text
/goal 期限切れセッションを受け入れてしまう不具合を修正する。境界時刻の直前・一致・直後を対象に再現テストを追加し、修正前に失敗・修正後に成功することを示す。有効なセッションの動作と、既存のエラー応答の形式は変えない。既存テストの期待値は変更しない。再現できない場合は、試した手順と不足している情報を報告して止まる。
```

（各ツールの入力欄で実行）

Claude Code では判定役がツールを使わないため、「テストが通る」だけでなく**テストの実行結果が会話に出ること**が完了の証拠になります。Claude Code の公式文書は、「`npm test` が終了コード 0」のように確かめ方を書き、「20 ターンで止める」のような回数の上限を条件に含める書き方を勧めています。

### 検証可能な小さな段階に分ける

1 つの `/goal` に調査から実装まで詰め込むと、どこまで確かめられたのかが分からなくなります。段階ごとに完了条件を分けます。

| 段階 | 完了条件の例 | 人が確認すること |
|------|------------|----------------|
| 調査 | 不具合を再現するテストが失敗する | 失敗の理由が想定どおりか |
| 仕様判断 | —（人が決める） | 境界の扱いを決め、主会話へ伝える |
| 実装 | 再現テストと既存テストがすべて成功する | 差分が守る条件の範囲に収まっているか |
| 検証 | lint・型チェックを含む CI 相当のコマンドが成功する | テスト以外の経路（手動確認・ログ）で動作が変わっているか |

仕様判断を `/goal` に含めないのは、判断を委譲しないためです。ここは[ループエンジニアリング](loop-engineering.md#落とし穴)の「判断は委譲しない」と同じ考え方です。

### テストを通すために期待値を変えていないか

完了条件を「テストが通る」にすると、エージェントがテストの期待値や対象を書き換えて条件を満たすことがあります。`/goal` が終わったら、次を必ず確認してください。

- 既存テストの**期待値**が変わっていないか（`git diff` でテストファイルを見る）
- テストが**スキップ**や対象の絞り込みで通っていないか
- 追加したテストが、修正前のコードで**実際に失敗する**か

防ぐには、完了条件に「既存テストの期待値は変更しない」「ほかのテストファイルは変更しない」と書いておくのが確実です。

### 目的を変える・止める・再開する

作業途中で目的がずれたら、そのまま続けずに目的を更新します。

| やりたいこと | Claude Code | Codex CLI | Copilot CLI |
|------------|-------------|-----------|-------------|
| 目的を直す | `/goal 新しい条件`（上書き） | `/goal edit` | `/goal 新しい目的`（目的の付け直し） |
| 一時停止 | 専用のコマンドはない。止めたいなら `/goal clear` で外し、後で設定し直す | `/goal pause` | `Ctrl+C` |
| 再開 | エラーで一時停止（`Goal paused`）した場合は、次のメッセージを送る | `/goal resume` | AI credit の上限で止まった場合は `/goal --max-ai-credits N` |
| 外す | `/goal clear` | `/goal clear` | `/goal off`（autopilot モードを解除） |

`/goal` は、待ち時間ごとに動く予定表ではありません。一定間隔で同じ作業を繰り返したいなら、Claude Code の `/loop` や Copilot CLI の `/every` など、時間で起動する仕組みを使います（[ループエンジニアリング](loop-engineering.md#実践の入口claude-code-の場合)を参照）。

## 1 つの修正で順番に使ってみる

期限切れセッションの不具合を例に、ここまでの操作を 1 本の流れにします。

| 順 | 操作 | 送り方 |
|----|------|-------|
| 1 | 完了条件を 4 要素で書き、再現テストの追加までを `/goal` に設定する | `/goal` |
| 2 | 実行中に「既存のエラー応答の形式は変えない」を思い出したので伝える | steer（Codex / Copilot は `Enter`、Claude Code は `Enter` でツールの切れ目に渡る） |
| 3 | テストが失敗する理由をサイドチャットで聞き、条件を変えた問いで理解を確かめる | `/btw` / `/side` / `/ask` |
| 4 | 境界の扱いを人が決め、結論と確認方法だけを主会話へ送る | steer または queue |
| 5 | 実装の完了条件で `/goal` を設定し直す | `/goal`（Codex は `/goal edit`） |
| 6 | 「終わったら CHANGELOG も更新して」を次のターンへ回す | queue（Codex は `Tab`、Copilot は `Ctrl+Enter`、Claude Code は `Enter`） |
| 7 | 別の修正方針も試したくなったら、会話を分岐して比べる | `/fork` / `/branch` |
| 8 | テストの期待値・差分・CI 相当の結果を人が確認する | — |

---

## 人が確認する項目

エージェントが説明し、テストを実行しても、判断と確認の責任は人に残ります。作業を終える前に次を確認してください。

- [ ] 実行中に送った条件が、差分に反映されているか
- [ ] サイドチャットで決めた仕様を、主会話へ送り直したか（サイドチャットの内容は主会話に残らない）
- [ ] `/goal` の完了が、会話上の報告ではなくテスト・コマンドの結果で示されているか
- [ ] 既存テストの期待値・対象を変えて通していないか
- [ ] 自動で進めたこと（エージェントが実行したこと）と、人が確かめたことを区別して記録したか
